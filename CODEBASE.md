## 2. AGENT CONTRACTS

### ingestion_agent.py
| | |
|---|---|
| **Reads** | `content: str`, `source_type: str` (passed directly, not from pipeline state) |
| **Writes** | Returns `{ chunks_stored: int, tags: list[str] }` on new content; `{ chunks_stored: int, tags: list[str], duplicate: True }` if content already exists — not a pipeline node |
| **Side effects** | Replace options: `refresh_unchanged` (routes, user-chosen Replace) replaces `replace_source_id` even when its text is unchanged, otherwise an unchanged text is a duplicate with no model calls (the business profile note); `replace_requires_same_text` (a target that matched only by text) raises `ReplaceMismatch` unless the new text is the target's, before any model call or write. First identifies the text's language (`utils/language.require_supported`, with the optional `reported_lang` from a provider): a source confidently in a language other than English raises `UnsupportedLanguage` before any model call or write (routes: 422; Obsidian: the note is skipped; business profile note: `memory_saved: false`); the result is stored as `sources.lang`. Computes SHA-256 hash of normalised content and calls `query_by_hash()` before any Claude call. If duplicate: returns immediately. If new: calls Claude for tag extraction, writes the `sources` row (status pending) and any Storage object from the required `original: SourceOriginal`, upserts chunks to Supabase `embeddings` with `source_title`, `ingested_at`, and `content_hash` metadata, then marks the row ready; a failure before that removes row, object and chunks. `replace_source_id` updates an existing source in place (business profile note). |

### frames.py — format_chunks_by_frame(), frame_rules(), decide_perspective()
| | |
|---|---|
| **Signatures** | `format_chunks_by_frame(chunks, profile) -> str`; `frame_rules(chunks, profile) -> str`; `decide_perspective(chunks, profile, *, opinion_only=False) -> str` |
| **Inputs** | Raw chunk dicts from `retrieval_bundle["chunks"]`; user profile dict |
| **Frame per chunk** | `chunk_frame()`: (1) consolidation chunks → CONSOLIDATION; (2) `memory_context`: `"work"` → PERSONAL_WORK, `"personal_project"` → PERSONAL_PROJECT, `"observation"` → OBSERVATION, `"learning"` → EXPERT_OUTSIDER or LEARNING_*; (3) legacy chunks without it: self-written source types → PERSONAL; (4) otherwise EXPERT_OUTSIDER when a tag overlaps the profile's expertise, else LEARNING_<SENIORITY> |
| **The frame list** | `FRAMES`: CONSOLIDATION, PERSONAL_WORK, PERSONAL_PROJECT, PERSONAL, OBSERVATION, EXPERT_OUTSIDER, LEARNING_SENIOR, LEARNING_MID, LEARNING_JUNIOR, each with the label its chunks get and the rule for writing from them. The block and the rules are generated from this list, so the prompt cannot describe frames the code does not produce |
| **Block** | Chunks grouped under their frame's label, each with `[source: <type> \| tags: <tags>]`. No title (stopgap, see section 6): external sources are referred to by type and subject. `(No notes relevant to this topic were found.)` when empty |
| **Perspective** | `experience` (all chunks self-authored), `learned` (all external), `mixed` (both), `opinion` (no chunks, or `opinion_only`) |

**Architectural decision — per-chunk frames prevent cluster contamination:**
The old cluster-level assignment caused one personal_note sharing a tag with article chunks to make ALL chunks in that cluster PERSONAL, leading to first-person hallucinations about externally-sourced content. Per-chunk assignment means each chunk carries only the frame that its own memory_context or source_type warrants. The memory_context field set at ingest time (via user pill selection or Haiku classifier) is the ground truth — source_type is the legacy fallback for existing chunks.

### predictability_audit_node (predictability_audit_agent.py)
| | |
|---|---|
| **Reads from state** | `current_draft`, `quality`, `user_id`, `retrieval_bundle`, `profile`, `topic`, `context`, `iterations` |
| **Writes to state** | `current_draft: str` (overwrites on any change; unchanged on any exception or when the specifics guard reverts); appends to `draft_history` whenever it writes `current_draft`; appends to `specifics_guard` when a retry was needed |
| **Side effects** | Up to 3 Claude API calls: Haiku (step 1, max_tokens=200) + Sonnet (step 2, max_tokens=200, only if not CLEAN) + Haiku (step 3, max_tokens=2000). **Sentence replacement logic:**
1. Exact string match (`original in post`) — `str.replace(..., 1)`
2. Fuzzy word-overlap: splits post into sentences, finds best match by `|orig_words ∩ candidate_words|`, requires overlap ≥ `max(1, len(orig_words) // 2)`
3. If no match found: logs WARNING and returns post unchanged

**Architectural decision — runs after humanizer, not before:**
The humanizer rewrites freely across the entire post, including sentence structure. Running the audit before humanizer would be wasted work — humanizer would overwrite the fixes. Running it after locks in the humanizer's voice pass first, then makes targeted single-sentence corrections on top of that final text. The audit is designed to be a scalpel (one sentence replaced, one rhythm break fixed), not a rewrite — which is why it sits at the end of the pipeline after all broader passes are complete.

### word_count_enforcer_node (word_count_enforcer_agent.py)
| | |
|---|---|
| **Reads from state** | `current_draft`, `length_target`, `quality`, `user_id` |
| **Writes to state** | `current_draft: str` (overwrites only if adjustment was needed; unchanged if within range, thread format, any exception, or the specifics guard reverts); appends to `draft_history` only when it adjusts; appends to `specifics_guard` when a retry was needed |

**Word count targets (via `state["length_target"]`; a first post is 70–100, thin sources are ceiling-only, and neither is ever expanded).** A LinkedIn post ignores the requested length: it stays under 200 words (`LINKEDIN_MAX_WORDS`, the hard limit; compress runs only past it), and the drafter is asked for `LINKEDIN_RANGE` (100–150; a first post 70–100 with a hard limit of 115). Pipeline A, the rollback, still uses the requested length from the table:
| Format | concise | standard | long-form |
|---|---|---|---|
| linkedin post (pipeline A only) | 100–180 | 250–350 | 450–600 |
| medium article | 350–500 | 700–900 | 1200–1800 |
| thread | — (tweet-based) | — | — |

**Architectural decision — word count enforcement is a separate final node, not a prompt instruction alone:**
Prompt-level word count instructions ("Target length: 100–180 words") are advisory — the model balances them against voice, structure, and substance requirements, and in practice generates 300–400 words regardless of the stated target. A final enforcement node is the only reliable mechanism because: (1) it counts words deterministically after all creative passes are complete; (2) it makes a single targeted edit (trim or expand) with no competing objectives; (3) it runs once, after all humanizer/scorer/retry iterations, so it never interferes with the quality loop. The node is positioned at the very end of the pipeline (after word_count_enforcer, only finalize runs) to avoid any pass undoing its enforcement.

### POST /generate

**Response:**

### Account and onboarding

- `GET /niches` (public): `{segments, other_niche, niches: [{key, label, pillars: [{key, label, about}]}], tones: [{key, label}]}`.
- `GET /account`: `{segment, business_niche, business_niche_other, business_profile, ask_segment, memory_saved}`. `ask_segment` is decided by the server.
- `PUT /account/segment`: `{segment: "business" | "individual", business_niche?, business_niche_other?, business_profile?}`. A business needs a listed niche (free text when `other`) and a profile: `business_name`, `service_area`, `services`, `tone` (a listed key), optional `website`, `differentiators`, `typical_customer`, `current_offers`, `tone_notes`. Invalid → 422, nothing saved. Response adds `memory_saved`: `false` means the answer is stored but the memory note failed.
- `POST /account/segment/skip`: records "Skip for now"; the question returns after 7 days.

### POST /generate additions

- Request: `pillar` (a key of the user's niche; 400 otherwise) and `pillar_details` (up to 4,000 characters; needs `pillar`). Details are ingested as a `personal_note` with `memory_context: "work"` before the pipeline runs.
- Quota: one generation is reserved before the pipeline and released if the result is not `"ok"` or the request fails. Out of quota → **402** `{detail: {code: "quota_exceeded", message, entitlements}}`.

### Billing

- `GET /billing/plans` (public): `{free: {generations_per_month, publishing}, pro: {generations_per_month, publishing, max_connected_accounts, price: {amount, currency, interval, trial_days} | null}}`. `price` is read from Stripe (cached 10 minutes) and is `null` when it cannot be.
- `GET /billing/entitlements`: `{plan, subscription_status, generation_limit, generations_used, generations_remaining, can_generate, can_publish, publishing_paused, max_connected_accounts, trial_end, current_period_end, cancel_at_period_end, period}`.
- `POST /billing/checkout` → `{url}` (Stripe Checkout, subscription mode, trial). 409 if already Pro. `POST /billing/portal` → `{url}`; 404 with no Stripe customer. 503 when Stripe is not configured.
- `POST /billing/webhook` (public; Stripe signature over the raw body): 400 on a bad signature, 200 `{received, outcome: processed | duplicate | ignored}`, 500 when handling fails (the event is forgotten so the retry is processed).

### Publishing

All need a token. A plan refusal is **402** `{detail: {code: "upgrade_required" | "payment_required", message, entitlements}}`. 503 when `PUBLISHING_PROVIDER` is unset.

- `GET /publishing/platforms`: `{platforms: [{platform, label, max_characters, media_required, max_images}]}`.
- `GET /publishing/accounts`: `{accounts: [{id, platform, label, display_name, status}]}`, synced with the provider.
- `POST /publishing/connect` `{platform}` → `{url}`. Needs a free account slot (402 otherwise).
- `DELETE /publishing/accounts/{id}`: allowed on any plan.
- `POST /publishing/media` (multipart `file`, image or video, 50 MB) → `{ref, kind}`.
- `POST /publishing/jobs` `{content, account_ids, post_id?, media, when: "now" | "schedule" | "queue", scheduled_at?, timezone}` → `{job}`. Validated against each target platform's rules: 422 `{detail: {code: "cannot_publish", problems: [...]}}`. Never publishes in the request.
- `GET /publishing/jobs` → `{jobs: [{id, post_id, content, account_ids, status, scheduled_at, published_at, created_at, results, message, error_code}]}`. `message` is a sentence the user can act on; the provider's own error text is never returned.
- `POST /publishing/jobs/{id}/cancel`: 409 once the job is publishing or finished.
- `POST /publishing/webhook` (public; the provider's signature): 400 on a bad signature.

## 5. KNOWN DECISIONS

| Decision | Why |
|----------|-----|
| Originals: text in `sources`, binaries in a private bucket (2026-10-16) | Text is small and re-ingestion reads it in bulk with SQL; files up to 10 MB would bloat the table and its 1,000-row reads. URL originals are Jina's unprocessed markdown, not page HTML: fetching pages from our backend adds an SSRF surface and is often blocked. Jina's HTML mode can be added per source later if the HTML is ever needed |
| Row before object before chunks, plus a sweeper (2026-10-16) | A `pending` row names the Storage path before the upload, so nothing can exist without a record; inline failures are cleaned up at once, and the sweeper (startup and hourly, pending over 30 min) covers process crashes. A bucket-listing cleanup job alone would have to diff every object against rows |
| Authorship order: user's choice, then rule, then classifier (2026-10-16) | Rules only where the input path settles it (business profile form, pillar details and onboarding story → `user_stated`). Planned with the classifier: high-confidence results applied automatically, shown and one-click editable; low confidence asks the user; the user's choice always wins. Backfilled rows stay NULL, and nothing reads authorship until the classifier is measured on quality_v1 |
| Bucket and table are deny-all to clients (2026-10-16) | Same pattern as every other table: only the backend's service role reads or writes; paths are per-user so per-user policies can be added if the frontend ever downloads originals directly |
| pgvector uses `upsert`, never `insert` | Prevents duplicate chunks if the same content is re-ingested; Supabase `upsert()` resolves on the `id` primary key |
| Score threshold is 75 | Defined in `pipeline/graph.py` as `SCORE_THRESHOLD = 75` |
| Humanizer retries capped at 3 (`MAX_ITERATIONS`) | Guarantees the pipeline always terminates; surfaces best attempt regardless |
| Embeddings are local (sentence-transformers) | No API key required, no per-call cost, adequate quality for retrieval |
| Vector search is an exact per-user scan, no ANN index (migration 013) | The IVFFlat index searched ~1% of all rows and filtered by user afterwards: recall@8 vs exact was 0.03 on the main production library. Libraries are small (largest 149 chunks), so exact is cheap; recall@8 vs exact is now 1.00 with latency within noise. Add an ANN index (HNSW with iterative scans) only when measured per-user scan time threatens the latency budget. Eval: `evals/baselines/2026-10-16-exact-vector-search.md` |
| YouTube ingest uses URL auto-fetch + manual fallback | The Feed Memory YouTube tab first tries `POST /fetch-youtube-transcript` from a pasted URL and shows a transcript preview on success; users can always paste transcript text manually if fetch is unavailable for a specific video. |

### Onboarding, publishing and billing (2026-10-13)

- **Business facts are sources, not profile.** A business's name, area, services and offers reach a post only through the "Business profile" note in the user's memory (`source_type: business_profile`, frame `BUSINESS_PROFILE`), so they are retrieved, cited and checked like any note. `state["business"]` carries only niche, tone and pillar. The coverage gate is unchanged.
- **Niche guidance lives in one place:** `config/niches.py`. The draft prompt's BUSINESS POST block is filled from it; no agent names a niche.
- **The publish queue is a Postgres table** polled by a loop in the web process, because the backend is one uvicorn worker with no Redis. Jobs survive restarts as rows; `FOR UPDATE SKIP LOCKED` stops two loops taking one job; each job's idempotency key is sent on every attempt.
- **Scheduled posts are held by us and sent at their time** (`publishNow`), not handed to the provider's scheduler, so cancelling and pausing for a failed payment need no provider call.
- **Subscription status is whatever Stripe says now.** Every subscription event triggers a fetch of that subscription, so late, repeated and out-of-order events converge. Nothing the browser sends changes a plan.
- **`past_due` is the grace period:** generation limit and accounts kept, publishing paused, scheduled jobs held. `canceled`, `unpaid` and `incomplete_expired` end the plan and cancel pending jobs.
- **The quota is reserved, then released,** so parallel requests cannot pass the limit and a request that makes no post costs nothing.
- **Prices are never in the frontend.** They come from `GET /billing/plans`, which reads the Stripe Price.

### Planned for `fix/ingest-attribution`

**Stopgap in place (from `fix/generation-alignment`):** sources are referred to by type and subject ("an article on…", "a talk on…") because stored metadata doesn't record whether a title is real. The title is not printed in chunk labels or prompts (`utils.frames.format_chunks_by_frame`, `agents.archetype_agent._material`); it stays in the generation trace (`retrieved[].source_title`).

**Proper fix: record where each title came from, and credit by title only when it is real.**
- Add `title_origin` (`provided` | `derived`) to `embeddings` (and `source_nodes`) in a new migration, and return it from the `match_embeddings` function so it reaches the retrieved chunks. Run the migration in both Supabase projects (production and eval), then re-seed the eval personas so their fixture titles are marked `provided`.
- Set it at ingest:
  - `provided`: URL scrape (page title), YouTube (video title), Obsidian folder or zip (note filename), any title the user types (`source_title` on `POST /ingest`), and file uploads.
  - **File uploads should store the filename as the title** (`provided`). Today `_title_from_text()` in `routers/ingest.py` uses the document's first sentence and falls back to the filename only when that is under 10 characters. This also changes what the Library card shows.
  - `derived`: a typed or pasted note with no title (first line, cut at 80 characters, in `ingestion_agent.ingest_content`) and images (first line of the extracted text).
- **Backfill existing rows deterministically:** for each source, re-run the same derivation on its first chunk (first line cut at 80 characters, and the first-sentence rule used for uploads) and compare with the stored title. Equal → `derived`; otherwise → `provided`. This compares against stored content; it does not guess from how a title looks. Rows that cannot be checked (first chunk missing) stay `NULL`, which is treated as not real.
- In the prompts: print the title in the chunk label only when `title_origin = 'provided'`, and restore "credit the source by its title" for those chunks; `derived` and `NULL` keep the type-and-subject wording.
